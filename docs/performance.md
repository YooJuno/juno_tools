# 성능·안정성 검토

2026-10-29, Ubuntu 24.04 / GNOME 46 / RTX 4060 Laptop GPU / NVMe 환경에서 확인했습니다. 비교 기준은 `3b867ef`이며 개선본은 확장 버전 4입니다.

## 측정 결과

상세 메뉴를 닫고 GPU 표시를 켠 상태의 센서 수집기를 독립 GJS 프로세스에서 실행했습니다. 준비용 2회 이후 10회를 측정했고, 각 반복 뒤 2초 대기했습니다. 전후 모두 같은 하드웨어·수집 항목을 사용했습니다.

| 측정 항목 | 변경 전 | 변경 후 |
| --- | ---: | ---: |
| 수집 호출 평균 | 34.78 ms | 2.07 ms |
| 수집 호출 중앙값 | 35.04 ms | 2.15 ms |
| 수집 호출 95백분위 | 41.43 ms | 2.73 ms |
| 검사 전체 CPU 시간(user + system) | 0.54 s | 0.08 s |

이 측정에서 평균 수집 호출 시간은 약 94%, CPU 시간은 약 85% 줄었습니다. 전체 GNOME Shell의 CPU 사용률이나 모든 장치에서의 성능 보장을 뜻하지 않습니다. CPU 시간은 `/usr/bin/time`으로 준비 단계·프로그램 초기화·종료 및 기다린 하위 프로세스까지 포함해 측정했습니다. 호출 시간은 센서 수집의 비동기 작업이 끝날 때까지의 경과 시간이며 UI 그리기는 포함하지 않습니다.

NVIDIA 데이터는 지정 주기로 갱신되는 스트림에서 가져오고 수집 호출에서는 최신 캐시를 사용합니다. GPU 프로세스를 재사용하는 대신 GPU 표시가 켜진 동안 프로세스 하나가 유지됩니다. 이 PC에서 해당 프로세스의 최대 상주 메모리는 약 23 MiB였습니다. 확장 전체의 추가 메모리 사용량으로 해석하면 안 됩니다. GPU 표시를 끄면 프로세스를 종료하며, GPU 절전 영향이 사라졌다고 주장하지 않습니다.

## 수정한 문제

- 매 갱신마다 `nvidia-smi`를 실행하고 NVML을 초기화하던 비용을 프로세스 하나의 반복 조회로 줄였습니다. 표준 출력은 비동기로 읽고, 최대 버퍼·장치 수 제한, 초기 응답 제한, 무응답 감지와 재시도 지연을 둡니다. 드라이버의 커널 I/O 때문에 종료되지 않는 자식 프로세스도 최대 4개로 제한해 재시도마다 무한히 늘지 않도록 합니다.
- 메뉴를 닫아도 온도와 디스크 I/O를 읽고 상세 문자열을 갱신하던 작업을 생략합니다. 숨긴 CPU/RAM/SSD 수집도 생략하며, 같은 글자·상태·경고 등급을 다시 설정하지 않습니다.
- CPU/RAM 파싱은 필요한 필드만 사용합니다. 디스크 I/O는 전체 `/proc/diskstats` 대신 해당 장치의 `/sys/dev/block/장치번호/stat`을 읽습니다. 파일 객체와 일부 센서 값을 제한된 크기로 재사용합니다.
- 느린 센서에는 시간 제한을 두고, 끝나지 않은 작업을 중복 실행하지 않습니다. 여러 경로로 바꾸더라도 미완료 디스크 작업을 최대 4개로 제한합니다. AMD 오류가 정상 NVIDIA 값을 가리지 않도록 나눴습니다.
- 수집 도중 설정을 바꾸거나 확장을 껐다 켰을 때 이전 결과가 새 화면을 덮어쓰지 않도록 세대를 확인합니다. 요청은 합쳐서 처리하고 동시 수집을 만들지 않습니다.
- 손상된 값, 없는 스왑 정보, 쉼표가 들어간 GPU 이름, 카운터 초기화, 잘못된 시간 간격과 마운트 변경을 처리합니다. 심볼릭 링크 경로의 용량과 I/O가 서로 다른 장치를 가리키던 문제도 수정했습니다.

## 갱신 정책

| 항목 | 정책 |
| --- | --- |
| CPU/RAM/표시 중인 GPU | 설정한 주기, 기본 2초 |
| SSD 용량 | 10초 캐시, 메뉴를 열 때 한 번 최신 조회 |
| 상세 메뉴의 디스크 I/O | 설정한 주기 |
| CPU 온도 | 메뉴가 열려 있을 때만, 5초 캐시 |
| 마운트/실제 장치 매핑 | 상세 메뉴에서 최대 30초 캐시 |
| CPU/AMD 센서 탐색 | 필요한 경우 최대 60초 캐시 |
| NVIDIA 오류 재시도 | 실패 후 30초 대기 |

메뉴를 처음 열거나 I/O 수집을 다시 시작한 첫 샘플은 읽기/쓰기 속도가 `—`입니다. 두 샘플의 실제 시간 차이로 속도를 계산합니다. 네트워크 파일시스템처럼 커널 작업이 오래 멈추는 상황에서 시간 제한은 UI 대기를 끝내는 제한이며, 커널 자체의 I/O 종료를 보장하지 않습니다. 같은 미완료 작업은 다시 쌓지 않습니다.

## 재현

저장소 루트에서 실행합니다. 외부 npm 라이브러리는 필요하지 않습니다.

```bash
/usr/bin/time -f 'CPU user=%U system=%S maxRSS_KiB=%M' \
  gjs -m tools/benchmark.js gnome-system-monitor/monitor.js 10 true false 2000
```

인수는 수집 모듈 경로, 측정 횟수, GPU 사용 여부, 상세 센서 사용 여부, 반복 후 대기 시간(ms)입니다. 동일한 스크립트에 비교할 이전 모듈 경로를 넘겨 비교할 수 있습니다. 이전 모듈의 상대 경로 import가 동작하도록 `metrics.js`도 같은 디렉터리에 두어야 합니다.

검증 명령:

```bash
npm test
gjs -m tests/collector-smoke.js
gjs -m tests/monitor-regression.js
gjs -m tests/nvidia-regression.js
bash tests/installer-smoke.sh
bash gnome-system-monitor/pack.sh
```

실제 GNOME 세션의 메뉴 열기·닫기, 표시 변경, 주기 변경, 밝은/어두운 테마, 확장 종료·재시작도 별도로 확인합니다.

## v0.5.3 느린 센서의 표시 지연 개선

2026-10-30, v0.5.2와 비교했습니다. 이전에는 CPU·메모리·GPU·저장장치의 전체 수집이 끝나야 한 번에 결과를 전달했습니다. GPU 초기 응답이 멈추면 이미 끝난 다른 센서의 결과도 GPU 작업의 시간 제한까지 기다렸습니다.

화면에서 사용하는 수집은 완료된 결과를 50 ms 단위로 묶어 먼저 전달합니다. 최종 결과·오류는 기존 시간 제한을 따릅니다. 대기 중인 항목은 기존 수치/로딩 표시를 유지하며 오류와 구분합니다. 빠른 센서가 모두 끝나면 예약한 중간 전달을 취소하여 최종 화면 한 번만 갱신합니다. 같은 수집을 계속 사용하므로 작업·프로세스·I/O 읽기를 추가하지 않습니다. 설정 변경·종료·새 세션 뒤의 결과를 버리는 검사와 GPU 선택 변경 시 다른 GPU 수치를 표시하지 않는 검사도 수행했습니다.

실제 `/proc`·`/sys`·파일시스템을 읽고 GPU 응답만 인위적으로 멈춘 GJS 재현 검사:

| 측정 항목 | v0.5.2 | v0.5.3 |
| --- | ---: | ---: |
| 정상 메모리·저장공간 결과의 최초 전달 | 3503.46 ms | 51.99 ms |
| 전체 수집 종료 | 3503.49 ms | 3504.88 ms |
| 중간 결과 전달 | 0회 | 1회 |

완료된 센서의 결과를 먼저 전달하여 지연을 줄였으며 GPU 작업의 시간 제한은 동일하게 유지합니다. 이 값은 GJS 콜백 전달 시간입니다. 화면 그리기 시간과 Thor의 실제 성능은 별도로 측정해야 합니다. 별도 GNOME 46 세션에서도 첫 GPU 수집에 800 ms 지연을 주고, 그 작업이 끝나기 전에 메모리 값이 상단에 표시되는 것을 확인했습니다.

정상 센서에서는 GPU 활성화·상세 수집·준비용 2회 뒤 10회·반복 간격 2초로 측정했습니다. 평균 수집 호출은 4.08 → 4.50 ms, 중앙값은 3.39 → 3.58 ms였고 CPU 시간은 0.15 → 0.17 s, 최대 상주 메모리는 약 28 MiB로 비슷했습니다. 중간 전달은 양쪽 모두 0회였습니다. 정상 상황의 CPU·메모리 절감을 주장하지 않으며, 중간 결과를 관리하는 소량의 오버헤드로 느린 센서 상황의 반응성을 개선합니다. 측정은 단회 비교로 백그라운드 부하 영향을 포함합니다.

```bash
# 실제 센서 + 응답하지 않는 GPU 테스트 대역. 드라이버 설정을 변경하지 않습니다.
gjs -m tools/latency-benchmark.js gnome-system-monitor/monitor.js
# 마지막 true로 UI와 같은 중간 전달 경로를 켭니다.
gjs -m tools/benchmark.js gnome-system-monitor/monitor.js 10 true true 2000 true
```
